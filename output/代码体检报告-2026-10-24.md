# 代码体检报告

**范围**：`learning_ext/`（14,152 行 Python）+ `custom_app.py`（196 行）+ `learning_ext/assets/`（4,541 行 JS/CSS）
**不含**：`kotaemon/`、`gradio`、第三方依赖——那些不是我们写的，改不动也不该改。

**方法**：
- `ruff` 全量（含 `flake8-bandit` 安全规则集 S、`mccabe` 复杂度 C90）
- AST 结构分析（函数长度、返回值元组规模）
- 关键路径人工走查：LLM 调用、门控判定、Gradio 事件绑定、计时心跳、Agent 工具、数据写入

**一句话结论**：
没有找到"能被外部攻破"的高危漏洞——应用绑在 `127.0.0.1`、没有对外接口、没有 SQL 拼接、没有 `eval`、LLM 输出进 HTML 前都过了 `html.escape`。
真正值得动的是 **3 个会算错数的地方** + **1 个已经埋进去的架构债**（9 元组返回值），后者已经害出过一次事故。安全上唯一需要警惕的是"动手学"，但它现在是关闭状态。

## 一、安全（按现实风险排序）

### S1. 动手学 Agent 等于给模型一个本机 shell，黑名单挡不住

**位置**：`agent/tools.py:67-105`、`agent/safety.py:28-51`、`practice/auto_setup.py:61-70`

`_ps()` 把命令字符串直接交给 `powershell -Command`，`run_command_streaming()` 也是一样。这些命令由 LLM 生成——也就是说，**模型能在这台机器上执行任意命令**。

现有的两道防线都不够硬：

1. **硬拦截是正则黑名单**（`safety.py` 里 14 条）。能挡住 `format c:`、`diskpart`、`shutdown` 这类"教科书式"命令，但挡不住：
   - PowerShell 编码绕过：`powershell -EncodedCommand <base64>`（黑名单只看字符串，看不到 base64 里的内容）
   - 别名与间接调用：`ri` / `rm` / `del` 等价于 `Remove-Item`；`Get-ChildItem C:\ | Remove-Item -Recurse`
   - 变量拼接：`$d = "$env:SystemDrive\"; Remove-Item "$d*" -Recurse`
   - 黑名单里 `remove-item ... [a-z]:\` 只匹配"盘符根直接跟反斜杠"，`C:\*` 或 `C:\ ` 的写法能绕过

2. **软确认是"一次点击"**。弹窗里还有"这次对话都允许"（`#le-coach-always`）——点一次之后整轮对话不再询问，而命令内容是模型现场生成的，用户未必逐条看。

另外 `_write_file()`（`tools.py:176`）可以写任意路径，没有白名单。配合 `run_command` 就是持久化能力（写启动项、写计划任务）。

**当前状态**：`pages/coach.py` 里 `COMING_SOON = True`，页面只渲染"开发中"说明页，事件没注册，这套能力**跑不起来**。

**建议**：真要把动手学放出来之前，至少做三件事而不是继续加正则：
- 命令执行改成"用户在弹窗里看到完整命令 + 明确点执行"，去掉"这次对话都允许"
- 文件写入加白名单目录（只允许工作区/桌面这类）
- 有条件就用 Windows Sandbox / 容器，别在宿主上直跑

### S2. 没有鉴权，安全性完全靠"只绑本机"

**位置**：`custom_app.py:190-196`

`launch()` 没有 `auth`，靠 `GRADIO_SERVER_NAME=127.0.0.1` 限制访问。这在本机自用场景是合理的，但：
- 一旦 `KH_GRADIO_SHARE` 打开（`share=True`），Gradio 会建公网隧道，任何人拿到链接就能读写你的库、调你的模型额度
- 如果有人把 `GRADIO_SERVER_NAME` 改成 `0.0.0.0` 想用手机访问，等于把整个学习库和 Agent 权限开在局域网上

**建议**：这两个开关要么锁死，要么在打开时强制要求 `auth=`。属于"低概率但后果重"，加个 `if SHARE and not AUTH: 拒绝启动` 就够。

### S3. 模型 API Key 明文存在 `.env`

**位置**：`pages/quick_setup.py:91-113`

`ENV_FILE.write_text(...)` 直接写明文，界面上也没有掩码处理。对一个本地单用户工具来说这是常规做法，不算漏洞，但值得知道：`.env` 一旦被同步到网盘/仓库/备份，key 就泄了。

**建议**：`operation` 上给 `.env` 加"不进 git"的确认（`.gitignore` 里有没有要看一眼），界面上回显时只显示后四位。

## 二、真 bug（会算错数、会卡、会悄悄失败）

### B1. 时区混用：「今天已学 N 分钟」在北京时间凌晨会算错

**位置**：`progress/gate.py:203` vs `:221-224`，`db/models.py:185`

```python
now = datetime.utcnow()                    # 203 行：UTC
...
today = datetime.now().date()              # 221 行：本地日期
if r.recorded_at and r.recorded_at.date() == today:   # 223 行：拿 UTC 日期比本地日期
```

`ProgressRecord.recorded_at` 的默认值是 `datetime.utcnow`（models.py:185），所以它存的是 **UTC 日期**；`today` 是 **本地日期（UTC+8）**。

**后果**：北京时间 0:00–8:00 之间，UTC 还停在前一天 → 这段时间的学习分钟**不计入"今天"**，反而算进昨天；同时"今天"显示 0。8 点以后两者日期一致，看不出问题——所以这个 bug 很容易一直不被发现。

**旁证**：现在库里 157 条 `study_minutes` 记录，`recorded_at` 全部是 UTC 时间（当前本地 20:14 = UTC 12:14，同一天，所以此刻显示正常）。

**改法**：统一成一套。要么全用 UTC 存、判断"今天"时先 `+8h` 再取 date；要么把 `recorded_at` 换成 `datetime.now`。两行的事。

### B2. `get_gate()` 是"先查再插"，没有唯一约束，并发下会插出两条

**位置**：`progress/gate.py:65-85`，`db/models.py:270-296`

```python
gate = session.exec(select(LessonGate).where(node_id=..., user_id=...)).first()
if gate: return gate
gate = LessonGate(...); session.add(gate); session.commit()   # 没有 unique 约束
```

`LessonGate` 只有 `index=True`，没有 `unique`。而 `get_gate()` 被两条路径同时调用：
- 每 30 秒一次的学习时长心跳 `add_dwell()`（`study_workbench.py:1696`）
- 用户点「已掌握」/「提交速测」/「提交复述」

两条路径撞在一起时（心跳刚 `select` 到空、还没 commit，用户此刻点了按钮），就会各插一条。之后 `.first()` 取到哪条不确定 → **可能出现"速测成绩记在 A 条、复述结果记在 B 条"，这一节永远过不了关**，而且从界面上看不出原因。

**改法**：加 `UniqueConstraint(node_id, user_id)`（新建表才有，老表要迁移），或者 `get_gate` 用 `try/except IntegrityError` 兜底。

### B3. 全局 `Semaphore(1)` 把所有并发压成一条线，交互请求要排后台备课的队

**位置**：`llm/client.py:27`、`progress/prep.py:19`、`progress/study.py:612`

```python
_REQUEST_SLOT = threading.BoundedSemaphore(1)     # 全局只允许 1 个 LLM 请求在飞
_WORKERS = 2                                       # 备课 2 个线程
max_workers: int = 3                               # 批量生成又开 3 个线程
```

三层并发叠起来，实际效果是 **1**。多开的线程只是在那等锁，白占内存和调度。

更要紧的是**交互被后台挤**：备课时队列里有几十节内容在排队，用户这时点「提交复述」或「换一组题」，也要排在这条 1 米宽的队后面。如果前面正在生成一节 8000 字的内容（60–120 秒），用户会觉得"点了没反应"。

**改法**（两个方向选一个）：
- 想要真并发：把 semaphore 放到 2–3（配合 API 限流），备课队列降为 1 个 worker，给交互请求留位置
- 想要稳：就承认是串行，把两层线程池删掉，代码直接很多（现在这写法是"看起来并发、实际没有"）

### B4. 学习时长记录无界增长，`gate_rhythm()` 每次全表扫

**位置**：`progress/service.py:118-135`、`progress/gate.py:213-224`

`record_study_time()` 每 30 秒**插入一条新记录**，从不合并。连续学 2 小时 = 240 条。现在库里已经 157 条（测试产生的）。

而 `gate_rhythm()` 算"今天多少分钟"的写法是：
```python
rows = session.exec(select(ProgressRecord).where(metric == "study_minutes")).all()   # 全表
for r in rows:  # Python 里逐条比日期
```
每次刷新工作台、每切一节、每 30 秒心跳后都会跑一次。**耗时随记录数线性增长**，用一年以后就是几万条记录每次全扫。

**改法**：用一个 SQL 聚合就够：
```sql
select sum(value) from progress where metric='study_minutes' and date(recorded_at)=:today
```
更好的做法是**按天 upsert 一行**（`metric='study_minutes_2026-10-24'`），一条记录替代一天的几百条——顺带把 B1 的时区问题也一起解决了。

顺带一提：这个心跳前端走的是隐藏桥（`#le-time-payload` + `#le-time-trigger`），也就是**每 30 秒一次完整的 Gradio 事件往返 + 两次 commit**（一次 progress、一次 gate.dwell）。之前"界面经常闪动"就是同一类问题，现在加了 `show_progress="hidden"` 掩盖住了，但请求量没降。把间隔从 30 秒放到 2–5 分钟、前端先攒着，体验和写入量都会好很多。

### B5. 9 元组返回值：已经害过一次事故，还会再害

**位置**：`study_workbench.py:1802 _try_master`（9 元组）、`:1028 _on_node_select`（8）、`:1930 _gate_skip`（7）、`review.py:249 _render`（9）

Gradio 的事件靠"返回值顺序 ↔ `outputs=[...]` 顺序"对应。只要有一项对不上，Gradio **不报错，直接静默丢值**。

历史上正是这个坑：`_try_master` 返回 9 项但 `outputs` 只写了 8 项，导致「点已掌握不跳转、点跳过能跳」——现象诡异，查了很久才发现是元组少了一个。

现在各处都对得上（我逐个数了），但这是**每次动这几个函数都要重新数一遍**的结构。加一个参数、改一个分支的返回，就可能悄悄坏掉。

**改法**（不用大改）：把"一大堆 UI 更新的打包"换成一个小数据类，或者让函数只返回"数据"，UI 刷新统一在一个地方做。至少要做到：early return 和正常 return 用同一个构造函数，不要手写元组。

### B6. `chat_json` 的容错正则太贪婪

**位置**：`llm/client.py:312-318`

```python
for pattern in [r"\{[\s\S]*\}", r"\[[\s\S]*\]"]:
```

`[\s\S]*` 是贪婪的，会从前一个 `{` 一直捞到最后一个 `}`。当模型返回的内容里含嵌套对象或多段 JSON（比如"这是诊断……{...}……再补充{...}"），截出来的是一段无效片段，`json.loads` 失败后直接抛 `ValueError("LLM 未返回有效 JSON")`——用户看到的就是这句。

**改法**：用括号配平扫描（从头找 `{`，计数 `{`/`}` 到归零），20 行以内，比正则可靠得多。

### B7. 用 `assert` 做运行时检查

**位置**：`practice/auto_setup.py:81`

```python
assert proc.stdout is not None
```

`python -O` 运行时 assert 会被整个删掉，这行变成"什么都没有"。这里只是给类型检查器看的，实际不会崩，但属于"用错工具"。改成 `if proc.stdout is None: return` 更准确。

## 三、过度复杂 / 可以更简单

### R1. `study_workbench.py`：2,132 行一个文件，`on_register_events` 334 行

**位置**：`pages/study_workbench.py:363`（334 行）、`:122`（238 行）

单文件里同时有：UI 构建（238 行）、事件绑定（334 行）、HTML 字符串拼装（`_rhythm_html`、`_gate_check_md`、`_build_node_header`）、业务逻辑（`_try_master`、`_gate_submit`、`_goto_next_after_gate`）、数据访问。改一个按钮要滚 300 行找绑定。

不是必须马上拆，但它和 B5 是同一个病根：**"页面"同时是 UI、控制器、视图层**。真要动，先拆出"数据/业务"（现在 `progress/` 已经有一部分），把 HTML 拼装挪到 `presentation.py`（那里已经有同类函数了）。

### R2. 三层线程池等于没有并发

见 B3。`prep.py` 的 2 个 worker + `study.py` 的 3 个 worker + `Semaphore(1)`，两处线程池都可以删掉，代码少 40 行，行为不变。

### R3. `apply_plan` 195 行，圈复杂度 29

**位置**：`progress/adapt.py:448`

一个函数里做：匹配旧节点 → 保留前段 → 重建后段 → 分配编号 → 处理依赖边 → 写快照 → 出报告。复杂度 29 意味着有近 30 条独立分支路径，测试几乎不可能覆盖全。

**改法**：按上面 7 件事拆成 7 个函数，`apply_plan` 只做编排。这也顺带解决"改一点要读 200 行"的问题。

### R4. 121 处 `except Exception`，其中 8 处直接 `pass` 什么都不做

`study_workbench.py` 一个文件 37 处。绝大多数是"兜底不让页面崩"，出发点是好的，但写法一致地粗糙：`except Exception: logger.exception(...)` 之后 `return gr.update()` ——用户看到的是"点了没反应"，日志埋在 debug 里。

真正危险的是那 8 处 `pass`：出了问题连日志都没有。

**建议**：加一个统一的 `fail(msg)` 帮助函数，异常时把一句话写到 `action_status` 上（界面本来就有这个位置）。用户至少知道"刚才那步失败了，原因大概是 X"。

### R5. 自研 markdown 渲染器（`coach.py` 约 200 行）

保留了代码块、表格、标题、列表、引用、粗斜体、链接的解析。**这块我不建议改**——它是为了绕开 Gradio `gr.Markdown` 的样式限制，而且 `_inline()` 先 `html.escape` 再处理格式，XSS 防护是对的。提一句只是让你知道：换成 `markdown` 库能少 150 行，但会丢掉现在这套精细的 CSS 类名。

## 四、检查过但**没问题**的地方（免得你担心）
