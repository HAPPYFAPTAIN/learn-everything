# 章节生成慢：问题定位与修复记录

**日期**：2026-11-08
**现象**：打开一节还没生成内容的课程，页面显示"正在写这一节…通常 30-60 秒"，实际等了十几分钟还没出来。
**结论**：不是模型慢，也不是生成逻辑慢——是**排队排在二十多节后面**。

---

## 一、先排除的两件事

排查时很容易直接怀疑"模型慢"或"提示词太长"，所以先把这两条量化掉。

### 1. 模型不慢

用当时的配置（`deepseek-chat`）直连测：一句话响应 **1.5 秒**。

### 2. 单节生成也不慢

| 环节 | 实测耗时 |
|---|---|
| `generate_node_summary()`（生成正文） | 21–22 秒 |
| `generate_node_summary_to_db(force=True)`（生成 + 写库 + 实操） | **20 秒**，6091 字，成功 |
| `environment_report()`（本机环境检测） | 0.9 秒 |
| 服务响应 | 正常（首页 1.33 MB） |

**一次生成就是 20 秒。** 那用户为什么会等十几分钟？

---

## 二、根因：打开项目时把整批章节一次性排进后台

问题在 `learning_ext/pages/study_workbench.py` 的 `_kick_project_prep()`：

```python
nodes = session.exec(select(KnowledgeNode).where(KnowledgeNode.project_id == pid)).all()
missing = [n.id for n in nodes if not is_content_valid(n.description)]
if missing:
    prep.start(pid, missing, topic)   # ← 一次把全部缺内容的节都排进队列
```

设计意图是好的（"打开项目就把没备课的章节丢后台，用户不用操心"），但有两个后果：

1. **全部入队**：新建一个 32 节的项目，绝大多数节只有建路线时留下的 36 字空壳，于是 **32 个任务全部进队列**。
2. **队列是先进先出**：用户点开第 3 节，那一节排在队列中后段，前面还有二十多节，按每节 20 秒算就是**十几分钟**。

再加上后台的 LLM 请求是**全局串行**的（`RequestGate`，一次只跑一个请求，为的是不被 API 限流、且用户请求能优先于后台），所以这二十多节是一节一节排队跑的。

**页面上的"通常 30-60 秒"只算了生成时间，没算排队时间**，这就是最误导的地方——用户以为卡死了。

---

## 三、修复

分两批：先把"生成本身"的浪费砍掉，再把"排队"解决掉。

### 第一批：生成本身的浪费（输出撞上限 + 无意义重试）

排查时还发现一个独立问题：提示词要求 2000–4000 字，但实际生成 7000–13721 字，中文 1 字约 1.3 token，直接撞上 `max_tokens=8000` 的上限；撞了之后被判为失败，外层还会重试 2 次，同样的提示词再来一遍还是超。

**改法：**

| 文件 | 改动 |
|---|---|
| `progress/study.py` | 提示词里的"2000-4000 字，宁可详细也不要简略" → **硬上限 4500 字**，并写明写不下时按什么顺序砍（先合并子主题 → 再减练习 → 最后压拓展）；删掉"简单知识点也要用丰富例子充实"这类鼓励写长的句子 |
| `progress/study.py` | 章节数量收紧：知识点深入 3-5 子主题 → 2-3；代码示例 2-3 → 2；误区 3-5 → 3；概念详解字数 150/100/100 → 120/80/80 |
| `progress/study.py` | 实操课程提示词加同样的字数硬上限 |
| `llm/client.py` | 新增 `OutputTruncatedError(RuntimeError)`，截断时抛这个类型 |
| `progress/prep.py` | 认这个异常 → **不重试直接放弃**（同样的提示词重排一遍大概率还是超，白等） |

**效果**：单节从"60–80 秒 × 2 次重试且经常失败"变成 **20–22 秒一次成功**。

### 第二批：排队（这次的真正问题）

| 文件 | 改动 |
|---|---|
| `progress/prep.py` | 新增优先队列 `_PRIORITY_Q`；`start(..., priority=True)` 的任务插到队首；worker 先取优先队列（`get_nowait`），空了再取普通队列（`get(timeout=0.5)`） |
| `progress/prep.py` | `task_done()` 改为对**实际取出的队列**调用（原来写死 `_Q`，优先队列会抛 `ValueError`） |
| `pages/study_workbench.py` | `_queue_single()`（用户点开某节时）改用 `priority=True` |
| `pages/study_workbench.py` | `_kick_project_prep()` **只预生成前 6 节**（原来全量），其余按需 |
| `pages/path_generator.py` | 新建路线后的入队同样只排前 6 节 |

**验证**：把真实生成 mock 掉，测执行顺序 → `[11, 12, 99, 13, 14]`。99 是用户点开的那一节，插到了第 3 位（前两个 worker 已经在跑，打不断，这是合理代价）。

## 四、修复前后对比

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 单节生成（顺利时） | 60–80 秒，且常常撞上限失败 | **20–22 秒一次成功** |
| 单节生成（撞上限时） | 60–80 秒 × 2 次重试，仍可能失败 | 不重试，直接报错，不浪费时间 |
| 打开新项目看第 N 节 | 等约 N×20 秒，第 30 节要十几分钟 | **最多等当前正在跑的那 1–2 节（≈20–30 秒）** |
| 新建 32 节项目 | 32 节全部排队（约 12 分钟） | 只预生成前 6 节（约 2 分钟），其余按需 |

## 五、给后续维护的几条经验

1. **"慢"要先分清是生成慢还是排队慢。** 办法很简单：在每层加时间戳，量一圈就知道卡在哪。这次量完发现生成只有 20 秒，问题全在排队。
2. **后台预生成必须有上限。** 不限量的话，用户等待时间会随项目规模线性增长——32 节的项目，用户看到的"卡住"就是十几分钟。
3. **提示词里一句"宁可详细也不要简略"，成本会直接翻几倍。** 模型会把它当成硬指标，输出量涨 2–3 倍，然后撞上限、重试、再撞。
4. **UI 上的时间承诺要和真实路径一致。**"通常 30-60 秒"只算生成时间、没算排队，是这次体验翻车的直接原因。
5. **截断（`finish_reason == "length"`）不该无差别重试。** 重试解决不了"写超了"这件事，只会在同一个地方再失败一次。
